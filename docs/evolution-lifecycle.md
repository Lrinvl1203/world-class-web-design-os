# What controlled evolution actually does

Passing evolution unit tests establishes their implemented contracts; it does not establish continuing design-quality improvement. Compare persistent, inspectable records and tested versioned changes with equivalent feedback conditions before claiming an effectiveness advantage.

The installer copies managed files on --overwrite; it does not delete every stale file from an older/newer installation. Therefore an in-place overwrite is not a proof of complete rollback. Use a fresh root for a clean rollback/version comparison, preserve project changes, verify doctor and the actual behavior, then choose the pinned CLI/skill root. No new security permissions or remote actions are needed for that local procedure.

## Persistent learning without inventing autonomy

1. Record an observed failure, relevant task/state, source/version, user impact and evidence path. Separate project taste, execution error, missing rule, bad rule and tool defect. Use the existing template; link the record from QA.md and the next project's context only if relevant.
2. For a reproducible tool bug, prepare the smallest diff and a prior positive plus new/negative regression. For broad design principles require repeated project evidence or independently reviewed external evidence. Never lower proposal thresholds to make one local failure look corroborated.
3. Run existing validators/tests and actual render/interaction checks where applicable. Record failed checks as well as repaired results. A synthetic fixture validates plumbing, not design transfer.
4. Intentionally decide adopt/trial/reject within authorized scope. Preserve the before version and exact after file hashes. Do not change weights or field gates to make the result pass.
5. Install the reviewed version to a new root. Start the next task there, load the relevant module/current-phase route and adopted record/version references. Prove the changed behavior is being used. Keep a clean known-good root to switch back to if regressions appear.

The bounded example here records the reproducible router budget failure and missing existing-module routes, tests a minimal patch, installs it into a clean temporary root and confirms a different task reads the corrected routing code/config. A separate clean before installation reproduces the old behavior for rollback. This is actual version-to-next-task plumbing, not a new agent design trial. A second synthetic history fixture invokes the real runEvolution offline: three explicitly synthetic source families yield a draft; two do not; neither edits any skill/config or adopts a rule. Synthetic URLs are never fetched and are never mixed with real evidence.

The continuous-learning and component-source-router modules already existed; adding their missing keyword entries connects them to the current router. The setup template's adopted-lesson field makes manual carry-forward explicit. No new autonomous learning engine, feedback database, automatic patcher or hidden memory is added.

## Proposed unseen-task evolution study — not executed

Freeze a before package and separate development/held-out tasks before training. Record all development failures and feedback. Only development evidence may propose a patch; require the existing analysis, prior/new/counterexample checks and intentional adoption. Freeze the resulting after package/hash before opening held-out briefs. Both evaluated arms use Web OS: one pins the unchanged before version, the other pins the reviewed after version. Keep the same model, tools, global-skill isolation, assets, prompt quality, budgets, browser and correction policy. Both may receive equal within-task feedback; the difference is the persisted approved version. Ordinary AI with equivalent feedback/memory can be an additional comparison, not a straw-man control.

Predeclare repeated-defect categories from development evidence (for example, contrast/overflow/critical-state failures) and count recurrence on at least four genuinely unseen archetypes with multiple runs per arm. Keep context-budget violations separate from rendered design defects. Include regression cases where the new rule could hurt, condition-blind visual review and actual task completion. Preserve initial/final code, all tool calls, failed attempts, correction counts, model/time/token use and manual interventions. A proposed layout is not a measured effect, and a passing training task is not a held-out success. Stop or revert an update that helps one case but harms others; report null/negative outcomes.

Before a scored trial, verify that a fresh agent can read the installed skill, write inside its test project, run and inspect local browser checks, and use the pinned version under the intended permissions. Record missing capabilities explicitly. The study above is a proposal; no held-out design-effectiveness result is established by these tools.
